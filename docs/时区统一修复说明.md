# 时区统一修复说明

## 📋 问题描述

### 现象
在Flutter APP中查看任务时，不同视图显示的时间不一致：

| 视图 | 数据库时间 | 前端显示 | 问题 |
|------|-----------|---------|------|
| **周视图** | 2025-10-15 09:00 ~ 2025-10-17 17:00 | **10月14-16日** | ❌ 早了1天 |
| **月视图** | 2025-10-15 09:00 ~ 2025-10-17 17:00 | **10月15-17日** | ✅ 正确 |
| **日视图** | 2025-10-15 09:00 ~ 2025-10-17 17:00 | **10月15-17日** | ✅ 正确 |

### 示例任务
**任务名称：** Q4绩效目标设定指导  
**数据库存储：**
- start_time: `2025-10-15 09:00:00`
- end_time: `2025-10-17 17:00:00`

**预期：** 所有视图都显示 15-17日  
**实际：** 周视图显示 14-16日（提前了8小时，即UTC+8时区差）

---

## 🔍 根本原因

### 时区转换问题

1. **数据库存储：** MySQL的DATETIME类型存储 `2025-10-15 09:00:00`，无时区信息
2. **后端返回：** 直接返回Date对象，转换为JSON时变成 `2025-10-15T01:00:00.000Z`
   - 这里的 `Z` 表示UTC时间
   - 但实际上应该是北京时间（UTC+8）
3. **前端解析：** Flutter的 `DateTime.parse()` 看到 `Z` 后，认为是UTC时间
   - UTC时间 `2025-10-15T01:00:00Z` = 北京时间 `2025-10-15T09:00:00+08:00` ✅
   - 但在周视图中，由于某些逻辑问题，导致显示为14日

### 时区转换流程图

```
数据库 DATETIME           后端处理              前端解析
2025-10-15 09:00:00  ->  ?????  ->  显示在哪一天？

修复前:
2025-10-15 09:00:00  ->  2025-10-15T01:00:00.000Z  ->  14日或15日（不确定）

修复后:
2025-10-15 09:00:00  ->  2025-10-15T09:00:00+08:00  ->  15日（确定）
```

### 核心思路
**在后端API返回时，明确标记时间为北京时间（UTC+8）**

#### 2. 时区转换工具函数（server_enterprise.js）

```javascript
// 时区处理工具函数
// 将MySQL返回的Date对象或字符串转换为北京时间的ISO字符串
function formatDateTimeForBeijing(dateTime) {
  if (!dateTime) return null;
  
  let date;
  
  // 如果已经是Date对象
  if (dateTime instanceof Date) {
    date = dateTime;
  }
  // 如果是字符串
  else if (typeof dateTime === 'string') {
    // 如果已经包含时区信息，直接返回
    if (dateTime.includes('+08:00')) {
      return dateTime;
    }
    // 解析字符串为Date对象
    date = new Date(dateTime);
  } else {
    return null;
  }
  
  // MySQL返回的Date对象已经是本地时区（北京时间GMT+8）
  // 我们需要获取本地时间的各个部分，然后标记为+08:00
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, '0');
  const day = String(date.getDate()).padStart(2, '0');
  const hours = String(date.getHours()).padStart(2, '0');
  const minutes = String(date.getMinutes()).padStart(2, '0');
  const seconds = String(date.getSeconds()).padStart(2, '0');
  
  // 组合成ISO 8601格式，明确标记为+08:00时区
  return `${year}-${month}-${day}T${hours}:${minutes}:${seconds}+08:00`;
}
```

## 💡 技术要点

### 为什么要明确标记时区？

#### 问题示例
```javascript
// MySQL存储：2025-10-15 09:00:00
// 如果直接返回，JSON序列化后：
"start_time": "2025-10-15T01:00:00.000Z"  // Z表示UTC，但时间变成了01:00

// Flutter解析：
DateTime.parse("2025-10-15T01:00:00.000Z")
// 结果：UTC时间2025-10-15 01:00，转北京时间 = 2025-10-15 09:00 ✅
// 但如果直接取日期部分，可能会出错
```

#### 解决方案
```javascript
// 明确标记为北京时间：
"start_time": "2025-10-15T09:00:00+08:00"

// Flutter解析：
DateTime.parse("2025-10-15T09:00:00+08:00")
// 结果：北京时间2025-10-15 09:00 ✅
// 日期部分始终是2025-10-15
```

### ISO 8601 时间格式

标准格式：`YYYY-MM-DDTHH:mm:ss±hh:mm`

示例：
- `2025-10-15T09:00:00+08:00` - 北京时间9点
- `2025-10-15T09:00:00Z` - UTC时间9点（= 北京时间17点）
- `2025-10-15T09:00:00` - 无时区信息（容易产生歧义）

### 前端解析

Flutter的 `DateTime.parse()` 能正确处理带时区的ISO 8601格式：

```dart
// 解析带时区的时间
DateTime dt = DateTime.parse("2025-10-15T09:00:00+08:00");
print(dt.year);   // 2025
print(dt.month);  // 10
print(dt.day);    // 15
print(dt.hour);   // 9 (在北京时区)
```

## ⚠️ 注意事项

### 1. 数据库字段类型
- 保持使用 `DATETIME` 类型
- **不要**改用 `TIMESTAMP`（会自动转换时区）
- 存储时按北京时间存储

### 2. 向后兼容
- ✅ 前端无需修改
- ✅ API格式保持不变（仍然是JSON）
- ✅ 只是时间字符串的格式更精确

### 3. 性能影响
- ✅ `formatDateTimeForBeijing` 函数非常轻量
- ✅ 只是字符串格式化，无复杂计算
- ✅ 对性能几乎无影响

### 4. 其他API
如果后续添加新的API端点，记得：
1. 在返回任务数据前，调用 `formatDateTimeForBeijing` 处理时间字段
2. 保持与现有API一致的时区处理方式
